# 设计验证：把 99 条真实 OCS 请求回放进新的 ingest

> 目的：新项目的 `ingest` 不能只靠"读源码觉得对"，必须用**真实的 OCS 请求**验证。
> 数据源：`../ocs-ai-answer-service-test/logs/answer-*.jsonl`，共 **99 条**真实请求，
> 字段就是 OCS 实际发来的 `title` / `options` / `type`。

---

## 一、选项解析：与旧解析器 97 条逐条对比，**零不一致**

新 `ingest` 放弃了"按 `\n` 切"，改成**按行首的序号标签切、无标签的行并入上一个选项**。
这样即使某个选项的 `innerText` 内部含换行，也不会被切多（见 OCS-CONTRACT.md §1.4 的隐患）。

在 97 条带选项的真实请求上，新旧解析出的选项条数**完全一致**，同时新解析器多了多行选项的兜底能力。

比较棘手的真实样本也过了：

```
'  A. 以技艺、官职为氏\n  B. 以封国、封邑为氏\n  C. 以事或物为氏\n  D. 以祖先名、字、谥号为氏\n  E. 以居住地为氏'
  → 5 个选项，A–E（已逐条核对，是真 5 选项而非多行被拆错）
```

## 二、题型推断：OCS 给 `unknown` 的 77 条是主战场

OCS 原始 `type` 分布：`unknown` 77 / `single` 16 / `multiple` 2 / `judgement` 2 / `completion` 2。

对那 77 条 `unknown`，把我们的形态推断与**模型当时的判定**（旧日志里的 `resolvedType`）对照：

| 我们的推断 | 模型当时判定 | 条数 |
| --- | --- | --- |
| `choice` | single | 32 |
| **`judgement`** | **judgement** | **27** |
| `choice` | multiple | 14 |
| `judgement` | single | 1 |

### 结论 A：判断题的形态规则**可用**

「选项恰好 2 个，且一个命中正确词表、一个命中错误词表」→ 判为判断题。
与模型判定一致 **27/28 = 96%**。

这条很重要，因为依据 OCS 源码，**判断题走的是关键词匹配，没有纯 ABCD 兜底**——
对这类题回字母会**必然失败**。旧项目靠 `${type}`，但这 30 条恰好全是 `unknown`，
等于旧项目在这 30 道题上一直在踩雷。

> 注意：模型判定只是**伪标签**，不是标准答案。96% 说明这条形态规则与模型的直觉一致，
> 不等于 96% 的客观正确率。真正要证明，需要人工标注的题集。

### 结论 B：单选/多选的区分**不能规则化**

14 条我们判 `choice` 的题，模型当时判为多选。我试过用题干信号词
（`哪些` / `哪几个` / `哪几位` / `分别` / `三个` / `包括` / `属于` …）去预测多选：

| 指标 | 结果 |
| --- | --- |
| 命中（预测多选且确为多选） | 6 |
| 误报 | 1 |
| **漏报** | **8** |
| 正确排除 | 31 |
| **多选召回率** | **43%** |
| 精度 | 86% |

漏报的真实样本：

```
西安事变的发动者是谁？（ ）            ← 实为多选（张学良、杨虎城），无任何词法线索
豫湘桂战役包含？（ ）                   ← "包含" 不在词表里
雅尔塔会议是由哪个国家参与的？（ ）      ← "哪个" 反而触发了单选特征
1931年6月至7月间，东北相继发生了（ ）？  ← "相继" 是复数信号但不是常见词
```

**所以：`choice` 必须交给模型判，绝不能默认单选。** 这也正是新 `ingest` 把
"选择题但单选多选未定"单独标成 `choice`（而不是猜一个）的原因。

### 结论 C：由此产生的最大风险

多选被误判为单选 → **只选一个，其余全丢**。

所以新设计里：
1. `type=choice` 时，prompt **强制**要求模型显式判定 `single` 还是 `multiple`；
2. `solve.js` 做一致性检查：模型自称单选却给了多个答案、
   或多选却只给一个 → 标记 `conflict`，降低可信度；
3. 宁可让模型对**每个选项独立判定**，答案集合 = 所有判为 `correct` 的选项，
   而不是盲信模型自己声明的题型。

### 结论 C 的落地实现（`src/reconcile.js`）

上面第 3 条最初只写在文档里，代码中并没有兑现——`letters` 完全取自模型自报的 `answer`，
`option_judgements` 被收集了却从未使用。现已补齐，策略如下：

| 情形 | 采用 | 理由 |
| --- | --- | --- |
| OCS 明确说 `multiple`，判定比答案多 | **并集** | 直接对着"漏选"这个主风险纠偏 |
| OCS 明确说 `single`/`judgement` | `answer`（取 1 个） | 单选多给会被 OCS 阶段 1 取第一个命中，风险更大 |
| 题型未定 + 两者一致 | 一致结果，按个数反推单选/多选 | 经过了一次交叉验证，最可靠 |
| 题型未定 + 两者不一致 | `answer`，标记冲突 | 不能确定谁对，**交给定向重问** |

**定向重问**（`solve.js` 的 `buildRecheck`）：只在"题型未定 + 不一致"时触发一次，
把有争议的选项标出来追问"到底还有没有别的正确项、这题是单选还是多选"。

采信门槛设置得很保守——重问结果**只在"给出了更多正确项"或"已达成一致"时才采纳**，
避免把一个本来答对的题改坏。

端到端实测：模型首次自报 `single` 且只给 `A,B`，但逐选项判定说 A/B/C 都正确
→ 判定与答案冲突 → 触发定向重问 → 模型改口承认 C
→ 最终 `letters: ["A","B","C"]`，`rechecked: true`。**漏掉的 C 被补回。**

## 三、怎么复现

```bash
cd ocs-answer-engine
node -e '/* 见本文档"复现脚本" */'
```

回放脚本读取 `../ocs-ai-answer-service-test/logs/answer-*.jsonl`，
对每条调用 `ingest({title, options, type})` 并汇总。核心就三行：

```js
const { ingest } = require('./src/ingest');
const q = ingest({ title: row.question, options: row.rawOptions, type: row.type });
```

## 四、这次回放没能验证的部分

- **emit 的正确性**：旧日志里只有旧服务返回的字母答案，没有"OCS 最终选中了哪个选项"的记录，
  所以无法从日志反推回写是否成功。这部分要靠 `src/ocs/matcher.js` 的单元测试来保证。
- **客观正确率**：模型判定是伪标签。要证明准确率，需要**人工标注**的题集
  （旧项目的 `eval/questions.json` 只有 20 题，且是自选的教科书名题，不代表真实分布）。
- **`ctx.type` 为假导致 OCS 不派发处理器**这一点（OCS-CONTRACT.md §8 旁注），
  需要在实际平台上观察页面是否被填答来确认。
